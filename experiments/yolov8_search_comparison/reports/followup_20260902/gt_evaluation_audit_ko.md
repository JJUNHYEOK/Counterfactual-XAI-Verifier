# GT 및 평가 파이프라인 감사

## 확인된 원인

기존 `gt_bboxes_log`는 절대 픽셀 `xywh` 형식의 MATLAB 1기반 프레임 로그였다. Python 평가기는 Ultralytics의 원본 영상 좌표 `xyxy`를 절대 픽셀 `xywh`로 변환해 클래스별 IoU와 AP@0.5를 계산했다. 좌표 형식 변환, letterbox 복원, 클래스별 매칭 자체에는 성능을 0으로 만들 오류가 없었다.

실제 오류는 GT 생성원이 렌더 영상과 달랐다는 점이다. `eo_camera_3d_render.m`의 주석도 MATLAB perspective 카메라와 핀홀 투영이 정확히 일치하지 않는다고 명시한다. 기존 박스는 휴리스틱 검출기의 넓은 내부 샘플링에는 쓸 수 있었지만 픽셀 정합을 요구하는 YOLO AP GT로는 부적합했다. 예를 들어 frame 1의 사람은 실제 가시 픽셀 박스가 `[364,127,17,32]`였으나 기존 투영 박스는 `[357.697,115.875,28.848,53.739]`였다.

수정은 객체 geometry를 확대·축소하지 않고 각 객체를 고유한 평면 색으로 다시 렌더한 뒤, z-buffer로 실제 보이는 픽셀의 외접 사각형을 얻는다. 평가 좌표는 0기반 절대 픽셀 `xywh`이며, 원래 투영 박스는 진단 필드 `legacy_projected_bbox_xywh`로만 남겼다.

## 수정 전후 수치

| 항목 | 기존 투영 GT | 렌더 인스턴스 GT |
|---|---:|---:|
| 총 박스 | 258 | 249 |
| 사람 박스 | 125 | 118 |
| 차량 박스 | 133 | 131 |
| 비양수 폭/높이 | 0 | 0 |
| 영상 범위 초과 | 76 | 0 |
| 일반 YOLOv8s mAP@0.5 | 0.000000 | 0.177966 |
| VisDrone YOLO11n 후보 mAP@0.5 | 0.050396 | 0.480903 |

기존 GT를 단순 클리핑해도 일반 YOLOv8s 0.000098, 후보 0.051204에 그쳤으므로 범위 클리핑은 원인 해결이 아니었다. 수정 GT에서 같은 프레임 정렬의 최대 IoU 및 TP 수가 인접 오프셋보다 높아, 한 프레임 밀림도 주원인이 아니었다.
